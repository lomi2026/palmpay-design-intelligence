03
AI 设计系统与设计开发一体化
AI 时代体验设计组织升级报告 · Module 03
Module 03 · AI Design System

让设计系统从“组件仓库”，
升级为“AI 可调用的生产基础设施”。

设计开发一体化的目标，不是让 AI 自由生成页面，而是让 AI 在统一业务规则、设计 Token、 组件规范和代码能力约束下，稳定生成可设计、可开发、可验证的产品方案。

本模块北极星目标
标准组件驱动的有效交付占比
新页面中，直接调用已治理组件、既有交互模式和代码能力完成，并通过自动化质量检查的交付占比。 它同时反映设计系统复用、AI 可调用程度、研发协作效率和上线质量。
一体化必须同时打通四个对象
业务规则AI 必须知道为什么用、何时用、不能怎么用。
设计资产Token、组件、模板、状态与内容规则结构化。
代码能力组件名称、属性、状态与前端 Props 一一对应。
质量验证自动检查视觉、状态、规范、风险和可访问性。
判断是否成功的标准：AI 生成结果能否直接使用标准组件，设计稿能否映射到代码，开发实现能否自动验证，而不是生成一张“看起来像设计稿”的图片。
01 · CURRENT PROBLEMS

为什么现有组件库无法直接支撑 AI 生成

多数团队的问题不是“没有组件”，而是组件缺少语义、规则、状态和代码映射，AI 只能模仿外观，无法稳定决策。
01 / DESIGN

设计资产只描述外观

组件库中有按钮、表格和弹窗，但缺少使用条件、禁用场景和业务规则。

  • 组件命名不统一
  • 状态与边界条件不完整
  • 同一模式存在多个变体
  • 缺少内容和数据规则
02 / DEVELOPMENT

设计与代码各自演进

Figma 组件与前端组件没有稳定映射，开发需要重新理解与实现。

  • Token 名称与代码变量不一致
  • Figma 属性与 React Props 不一致
  • 前端状态比设计多或少
  • 设计变更无法同步到代码
03 / AI

AI 缺少可执行约束

AI 读取整份 Figma 文件后信息量很大，但仍不知道应该选择哪个组件。

  • 无法判断业务场景
  • 自由组合导致规范漂移
  • 生成结果不可追溯
  • 无法直接进入研发流程
02 · TARGET ARCHITECTURE

AI 设计系统的五层架构

从业务语义到质量验证，任何一层缺失，都会让 AI 生成停留在概念稿阶段。
LAYER 01

业务语义层

用户角色与权限
业务流程与规则
字段与数据定义
合规与风险约束
解决“为什么这样设计”
LAYER 02

设计基础层

Color / Type / Spacing Token
栅格与响应式规则
图标与动效规范
内容与语气规范
解决“视觉如何统一”
LAYER 03

组件与模式层

基础组件
业务组件
页面模板
复杂任务模式
解决“AI 应该调用什么”
LAYER 04

代码映射层

组件名称映射
Props 与状态映射
Storybook 文档
代码示例与测试
解决“如何直接开发”
LAYER 05

AI 与质量层

组件检索与推荐
规则校验与解释
设计稿生成
还原度与状态检查
解决“如何规模化稳定产出”
03 · COMPONENT SCHEMA

每个组件必须补齐 12 类结构化信息

AI 不需要优先读取整个组件库，而需要检索一份结构化、低噪声、可引用的组件说明。

AI 可读组件模型

以下字段同时服务设计师、产品经理、前端工程师和 AI。

01组件名称统一英文名、中文名和唯一 ID。
02业务目的解决什么任务与用户问题。
03适用场景何时应该使用该组件。
04禁止场景何时不能使用，替代方案是什么。
05属性与变体尺寸、类型、方向、层级和配置。
06状态默认、悬停、加载、错误、禁用等。
07内容规则文案、字段、数据长度和格式。
08交互规则触发、反馈、确认、撤销和容错。
09布局规则间距、对齐、响应式和组合方式。
10风险与无障碍高风险确认、键盘、焦点和读屏要求。
11代码映射React 组件、Props、Token 和示例。
12AI 调用说明检索关键词、选择逻辑和输出限制。

示例：Amount Input

适用于支付、退款、换汇和充值等金融场景。

component_id: finance.amount-input name: AmountInput business_goal: - 帮助用户准确输入货币金额 use_when: - 支付 - 退款 - 换汇 - 账户充值 do_not_use_when: - 输入百分比 - 输入普通数量 props: currency: ISO-4217 precision: by_currency min: 0 max: business_rule states: - default - focus - filled - error - disabled - loading content_rules: - 显示货币符号或代码 - 输入时使用千分位 - 精度由币种决定 interaction_rules: - 不允许负数 - 金额为 0 时禁止提交 - 错误必须给出修复方式 code_mapping: package: @company/finance-ui component: AmountInput figma_property_map: size: size status: status currency: currency ai_instruction: - 优先调用标准组件 - 不得自行创建新的金额输入样式 - 高风险提交前必须二次确认
04 · FIGMA TO CODE

Figma、设计 Token 与代码组件必须一一映射

一体化不是“从 Figma 导出代码”，而是建立稳定的命名、属性、状态与版本关系。
01 / TOKEN MAPPING

设计 Token 同源

颜色、字体、间距、圆角、阴影和动效使用统一语义命名。

Figma Variablecolor.text.primary
Token JSONcolor.text.primary
CSS / Theme--color-text-primary
自动校验禁止硬编码色值
02 / COMPONENT MAPPING

组件属性同构

Figma 属性与前端 Props 保持相同语义和可选值。

Figma ComponentButton
Propertytype=primary
React Component<Button type="primary">
Storybook自动展示全部状态
03 / VERSION MAPPING

版本与变更可追溯

组件升级必须说明影响范围、迁移方式和兼容周期。

设计版本v2.3
代码版本@company/ui 2.3
变更日志Props / 状态 / Token
弃用策略迁移指引 + 截止日期

06 · GOVERNANCE

组织分工与治理规则

组件治理不能只由设计团队维护，必须形成设计、前端、产品和业务共同负责的机制。

关键角色

设计系统负责人
负责组件架构、规范、版本、采用率和跨产品一致性。
设计工程师
连接 Figma、Token、代码组件、自动化工具和发布流程。
前端组件负责人
负责代码实现、测试、Storybook、性能和版本兼容。
业务体验设计师
沉淀业务组件、流程模式、状态规则和真实使用反馈。
AI 工作流负责人
维护检索、Prompt、组件选择规则、评测集和生成质量。
质量与无障碍 Owner
定义上线门禁、视觉验收、状态完整性和无障碍标准。

六条治理规则

1
新增组件必须证明不可复用优先扩展现有组件和模式，避免重复建设。
2
设计与代码必须同步发布不能只更新 Figma，也不能只更新前端组件。
3
状态不完整，不允许标记为可用至少覆盖默认、交互、加载、错误、禁用与空状态。
4
组件规则必须可被机器读取规范不能只存在于长文档和口头经验中。
5
AI 生成结果必须记录来源可追溯调用了哪些规则、组件、版本和数据。
6
采用率与问题数据决定迭代不以组件数量衡量设计系统价值。

09 · 90-DAY ROADMAP

90 天落地路线图

先治理 20—30 个高频核心组件与 2—3 个关键页面模板，不建议一开始重做全部组件库。
DAY 01—30

统一底座

确认范围、命名、Token、组件优先级和代码现状。
  • 盘点 Figma 与代码组件差异
  • 确定统一组件命名与唯一 ID
  • 统一核心 Token 命名
  • 选定 20—30 个高频组件
  • 确定 Amount Input、Table、Modal 等试点组件
交付物：资产盘点、组件优先级、Token 字典、差异清单、治理责任人。
DAY 31—60

结构化与映射

补齐 AI 可读规范，完成 Figma 与前端属性、状态和版本映射。
  • 为试点组件补齐 12 类信息
  • 建立 Figma Property 与 React Props 映射
  • 完善 Storybook 状态与示例
  • 建立 Token JSON 与发布流程
  • 创建组件检索与推荐原型
交付物：结构化组件文档、代码映射表、Storybook、AI 检索原型。
DAY 61—90

进入真实项目

使用新系统完成实际页面，并通过自动质检验证价值。
  • 选择一个核心业务流程试点
  • AI 推荐组件并生成结构方案
  • 输出代码映射与实现说明
  • 接入视觉、状态与规范检查
  • 复盘效率、采用率和缺陷变化
交付物：真实上线案例、结果报告、问题清单、下一阶段扩展计划。
